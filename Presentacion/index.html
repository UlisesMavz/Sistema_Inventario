Justificación

¿Por qué este proyecto? Desarrollar un sistema de inventario funcional —con autenticación de usuarios, operaciones CRUD completas, panel de administración y una interfaz de usuario estética— obliga al equipo a aplicar los algoritmos en un contexto concreto, con datos reales y con la restricción adicional de que el entorno de ejecución no es un arreglo en memoria sino una base de datos relacional.
La capa de complejidad extra Este punto introduce una capa de complejidad inusual en los proyectos académicos: los algoritmos deben recuperar los datos de MySQL y operar sobre ellos en PHP, lo que añade el concepto de transferencia de datos entre capas al análisis de rendimiento.

Objetivo General

Meta del proyecto Diseñar, implementar y analizar un sistema web de gestión de inventario que demuestre la aplicación práctica de algoritmos clásicos de ordenamiento y búsqueda sobre una estructura de datos persistida en una base de datos relacional, empleando arquitectura MVC y metodología ágil colaborativa.
PHP + MySQL Arquitectura MVC API RESTful Metodología Ágil

Diseño de Casos de Uso

Patrón de Arquitectura MVC

Su propósito central es la separación de responsabilidades: el Modelo gestiona los datos y la lógica de negocio; la Vista se encarga de la presentación y la interacción con el usuario; el Controlador actúa como intermediario, recibiendo las acciones del usuario, invocando la lógica del Modelo y seleccionando la Vista adecuada para la respuesta.

👁 Vista (public/) Frontend compuesto por archivos HTML5 estáticos (index.html, dashboard.html) vinculados a CSS externos y scripts JS. La única comunicación con el servidor es a través de Fetch API que consume los endpoints REST. Esta separación garantiza portabilidad a cualquier cliente.
⚙ Controlador (controllers/ + api/) Los controladores (AuthController.php, ProductoController.php) contienen la lógica de negocio: autenticar usuarios, insertar/eliminar productos, invocar algoritmos y devolver respuestas JSON. Los archivos api/ actúan como routers que validan el método HTTP y la sesión activa.
🗄 Modelo (models/) Las clases Producto.php y Usuario.php representan las entidades del dominio. Cada clase encapsula atributos, un método de validación de datos y métodos de conversión (toArray(), fromArray()) para facilitar la serialización JSON. El Modelo no contiene lógica de acceso a la BD.

Bases de Datos Relacionales y Modelo E-R

¿Qué es una BD Relacional? Organiza la información en tablas (relaciones) cuyos datos están inter-relacionados mediante claves primarias y foráneas. El modelo relacional garantiza la integridad referencial, permite consultas declarativas mediante SQL y asegura las propiedades ACID.
Entidades del sistema HA&KU usuarios: credenciales con contraseña hasheada Bcrypt (password_hash())
productos: inventario con campos id, posicion, codigo, nombre, precio, stock, stock_minimo, categoria, marca_proveedor
Índices para rendimiento Los índices definidos sobre posicion, codigo y nombre aceleran las consultas de ordenamiento y búsqueda a nivel de BD, complementando los algoritmos en la capa de aplicación.

Simulación de Lista Enlazada en BD Relacional

¿Qué es una Lista Enlazada? Estructura lineal donde cada nodo contiene un dato y un apuntador al siguiente nodo. Sus operaciones características:
Cabeza: O(1) · Cola: O(1) con tail ptr · Posición k: O(k) · Eliminación cabeza: O(1) · Búsqueda: O(n)
El problema con BD Relacionales Las BD relacionales no contemplan nativamente una estructura equivalente a la lista enlazada. Los registros de una tabla no tienen un orden garantizado salvo el especificado explícitamente en la cláusula ORDER BY.
Estrategia adoptada: campo posicion Campo posicion (INT, NOT NULL): Cada producto almacena un entero que representa su lugar en la secuencia lógica. La consulta SELECT * FROM productos ORDER BY posicion ASC reproduce fielmente el recorrido de una lista enlazada de cabeza a cola.
Inserción en Cabeza — O(n) UPDATE productos SET posicion = posicion + 1;
Luego: INSERT INTO productos (..., posicion) VALUES (..., 1);
O(n) por la actualización masiva.
Inserción en Cola — O(1) SELECT MAX(posicion)+1 AS nueva FROM productos;
Luego INSERT con esa posición. O(1) si MAX está indexado.
Inserción en Posición k UPDATE productos SET posicion = posicion + 1 WHERE posicion >= :k;
Luego INSERT (..., posicion) VALUES (..., :k);

Algoritmos de Ordenamiento — Bubble Sort

¿Cómo funciona? Funciona comparando pares de elementos adyacentes e intercambiándolos si están en el orden incorrecto, repitiendo el proceso hasta que el arreglo esté ordenado. Los valores mayores "burbujean" hacia el final en cada pasada.
Complejidad Peor caso: O(n²) — arreglo invertido
Caso promedio: O(n²)
Mejor caso: O(n) — ya ordenado (con bandera)
Espacio: O(1) — in-place
Estabilidad: Estable ✓
Implementación en PHP Implementado con la optimización de bandera ($huboIntercambio) que detecta cuando el arreglo ya está ordenado y termina anticipadamente, logrando O(n) en el mejor caso. Sin uso de sort() nativo.

Algoritmos de Ordenamiento — Quick Sort

Divide y Ganarás El Quick Sort selecciona un elemento como pivote y reordena el arreglo de manera que todos los elementos menores al pivote queden a su izquierda y todos los mayores a su derecha. Luego se aplica recursivamente a cada subconjunto.
Complejidad Peor caso: O(n²) — pivote siempre mínimo/máximo
Caso promedio: O(n log n)
Mejor caso: O(n log n)
Espacio: O(log n) en pila de recursión
Estabilidad: No estable
Ventaja sobre Bubble Sort En las pruebas del sistema, Quick Sort fue ~3.5× más rápido que Bubble Sort para n=100 productos (0.6 ms vs 2.1 ms). La diferencia crece con n, siguiendo la predicción teórica O(n log n) vs O(n²).

Algoritmos de Búsqueda

🔍 Búsqueda Lineal La búsqueda lineal (o secuencial) recorre cada elemento de la colección comparándolo con el valor buscado hasta encontrarlo o agotar la lista. Es el algoritmo de búsqueda más simple y funciona sobre cualquier colección, independientemente de su orden.
Peor caso: O(n) · Promedio: O(n/2) · Mejor caso: O(1)
⚡ Búsqueda Binaria La búsqueda binaria es un algoritmo de alta eficiencia que opera sobre colecciones previamente ordenadas. En cada paso divide el espacio de búsqueda a la mitad, comparando el elemento del centro con el valor buscado y descartando la mitad que no puede contenerlo.
Peor caso: O(log n) · Promedio: O(log n) · Requisito: colección ordenada

API REST (Representational State Transfer)

REST es un estilo arquitectónico para sistemas distribuidos. No es un protocolo ni un estándar, sino un conjunto de seis restricciones de diseño que producen sistemas web altamente desacoplados, escalables e interoperables.

① Cliente-Servidor Separa la interfaz del usuario del almacenamiento de datos para que ambos evolucionen por su cuenta de forma independiente.
② Sin Estado (Stateless) Cada petición debe ser autosuficiente. En HA&KU se logra enviando la sesión PHP en cada llamada mediante credentials: 'include' de Fetch API.
③ Caché Las respuestas indican si pueden guardarse. Se usa no-cache en rutas críticas para proteger datos sensibles del navegador.
④ Interfaz Uniforme Los recursos se gestionan de forma estándar mediante URIs únicas y verbos HTTP (GET, POST, PUT, DELETE).
⑤ Sistema en Capas El cliente interactúa con la API sin importar si hay intermediarios como proxies o balanceadores en medio.
⑥ Código Bajo Demanda El servidor puede mejorar la funcionalidad del cliente enviando scripts ejecutables (como JavaScript).

Conclusiones

① Lenguaje vs. Algoritmo El entorno de ejecución (PHP vs C++) afecta más al rendimiento real que la lógica del algoritmo. Un mismo algoritmo puede ser muy lento en un lenguaje interpretado, aunque su Big-O sea idéntico.
② Estructuras en BD Implementar una lista enlazada en SQL es posible, pero sacrifica eficiencia (inserciones O(n)) a cambio de persistencia de datos y atomicidad de transacciones.
③ Trabajo en Equipo El uso de MVC y una API permitió que backend y frontend avanzaran en paralelo sin conflictos, usando la API como contrato de comunicación entre integrantes.
④ Seguridad La seguridad debe estar en el servidor. Un error demostró que validar solo en el cliente (con localStorage) no sirve, porque el usuario puede manipular el navegador. La sesión PHP en el servidor es la verdadera barrera.
⑤ Metodología Los sprints semanales y las reuniones cortas fueron clave para organizar el trabajo, adaptarse a problemas y mantener al equipo sincronizado durante todo el ciclo de desarrollo.
